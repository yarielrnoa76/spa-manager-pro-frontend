# ADR-005: Tailwind CDN → Local Vite/PostCSS Pipeline

| Property | Value |
| --- | --- |
| Status | `ACCEPTED` |
| Date | 2026-08-23 |
| Repository | `spa-manager-pro-frontend` |

## Context

Since project inception, Tailwind CSS was loaded in `index.html` via the public Play CDN:

```html
<!-- Tailwind CDN (temporal, luego lo podemos integrar formalmente) -->
<script src="https://cdn.tailwindcss.com"></script>
```

No `tailwind.config.*` file, no `postcss.config.*` file, and no `tailwindcss` npm package existed in this repository. The comment in the source itself already flagged this as temporary.

## Problem with the Play CDN

- The Play CDN compiles Tailwind's utility CSS **in the browser, at runtime**, using a `<script>` tag that must run before first paint.
- It is explicitly documented by Tailwind Labs as intended for prototyping/development, not for a Production dependency: it ships an unpinned, frequently-changing build, adds a render-blocking external network request on every page load, and cannot be content-scanned, purged, or bundled by a build tool.
- Because no version was pinned, the exact ruleset generated by the CDN could silently change between visits, with no reproducible build artifact for QA/Production parity checks.

## Decision

Tailwind CSS is pinned to the **exact** version `3.4.18`, compiled locally via PostCSS inside the existing Vite build pipeline. `postcss` (`8.5.6`) and `autoprefixer` (`10.4.21`) are added as pinned, non-floating `devDependencies` alongside it. The Play CDN `<script>` tag is removed from `index.html`.

Configuration added:
- `tailwind.config.cjs` — `content` scans `./index.html` and `./src/**/*.{js,ts,jsx,tsx}`; `theme.extend` is empty (no inline Tailwind configuration existed in `index.html` to migrate — confirmed by inspection before this change).
- `postcss.config.cjs` — registers the `tailwindcss` and `autoprefixer` plugins.
- `src/index.css` — gained `@tailwind base; @tailwind components; @tailwind utilities;` as its first three lines, ahead of all pre-existing custom CSS in that file, which is otherwise untouched.

Both config files use the `.cjs` extension because `package.json` declares `"type": "module"`; a plain `.js` extension would be parsed as an ES module by Node, and Tailwind/PostCSS's v3-era config format is CommonJS (`module.exports = {...}`).

## Why not Tailwind v4 in the same change

Tailwind v4 changes its configuration model (CSS-first `@theme` configuration, a new engine, and — critically — its own first-party Vite plugin `@tailwindcss/vite` as the recommended integration path, replacing the PostCSS-based setup used here). Combining "stop using an unpinned browser-runtime CDN" with "adopt a different major version's entirely different configuration and build model" in one change would make any visual regression impossible to attribute to one cause or the other. This migration's only goal is removing the Play CDN and reproducing current v3 behavior with the lowest possible risk. A Tailwind v4 migration remains a distinct, future, separately authorized decision (Addendum 01, D-12).

## Affected files

- `package.json`, `package-lock.json` — three new pinned `devDependencies`: `tailwindcss@3.4.18`, `postcss@8.5.6`, `autoprefixer@10.4.21`. No other dependency was added, removed, or changed version.
- `tailwind.config.cjs` — new.
- `postcss.config.cjs` — new.
- `index.html` — CDN `<script>` tag and its comment removed; nothing else changed.
- `src/index.css` — three `@tailwind` directives prepended; every pre-existing rule preserved verbatim below them.

No `.tsx`/`.ts` component file was modified by this change (see next section).

## Dynamic-class strategy

Before making any change, the full inventory required by D-07 was performed across `index.html` and all of `src/`, specifically targeting:

- Template-literal fragment construction (e.g. `` `bg-${x}-100` ``): **zero occurrences found**, confirmed by targeted pattern search for a Tailwind utility prefix immediately adjacent to `${`, and for `${...}` immediately adjacent to a shade/suffix token.
- String concatenation building a class name from parts (`"bg-" + x + "-600"`): **zero occurrences found**.
- Arbitrary-value bracket interpolation (e.g. `` w-[${x}px] ``): **zero occurrences found**.
- The one component whose signature originally raised suspicion, `src/components/StatCard.tsx`, does interpolate a `color` prop into its className (`` `p-3 rounded-lg ${color} text-white flex-shrink-0` ``), but every caller across the codebase (`Expenses.tsx`, `Dashboard.tsx`, `Refunds.tsx`, `RevenueTab.tsx`) passes a **complete, literal, statically-present** class string (e.g. `"bg-indigo-600"`, `"bg-emerald-600"`) as that prop. Tailwind's v3 content scanner is a plain-text regex scan of the configured `content` globs — it does not evaluate JavaScript — so as long as the complete class string appears verbatim anywhere in a scanned file (which it does, as a literal prop value), it is detected and included in the generated stylesheet with no `safelist` entry required.
- One exception was found and is **explicitly not fixed by this ADR**: `src/pages/Tickets.tsx` passes bare color names (`color="indigo"`, `"blue"`, `"amber"`, `"red"`) to the same `StatCard`, which never resolved to a valid Tailwind utility even under the old CDN (a bare color name matches no Tailwind utility pattern with or without a build step). This is a pre-existing defect, and `Tickets.tsx` is additionally not reachable through any route or navigation entry in the current application (see `Phase0_1_Decision_Resolution_and_Mapping_Review.md`, decision D-11) — so this migration introduces no new, user-visible regression, and per this work package's explicit exclusions (no Tickets changes, no unrelated refactors), it is left untouched and only recorded here for traceability.

**Conclusion: no `safelist` entries and no source-code class refactor were required.**

## Consequences

- The frontend no longer depends on an external, unpinned, render-blocking script for its core styling at Production runtime.
- Tailwind's generated CSS becomes a versioned, reproducible build artifact inside `dist/`, inspectable and diffable like any other bundled asset.
- Future work (Brand & Experience Studio, AI Studio, and other UI from Part VII) can now build on a real, purgeable, themeable Tailwind configuration instead of an unversioned CDN.
- This ADR does **not** introduce `clsx`, `tailwind-merge`, or any shared design-system layer — those remain explicitly out of scope per D-12.

## Rollback

Revert this change set (config files, `index.html`, `src/index.css`, `package.json`/`package-lock.json`) to restore the Play CDN `<script>` tag and remove the local Tailwind toolchain. No data, schema, or runtime state is affected — this is a frontend build-tooling change only.
